# Security

## What SlopBar can access

SlopBar reads the sign-in files that Claude Code and Codex already keep on your PC, in your Windows profile and in each WSL distro. The existing account-switching vault copies full login data, including refresh tokens, into JSON files under `%APPDATA%\dev.thelio.slopbar\accounts`. **That legacy vault is still plaintext.** This telemetry fix does not encrypt or redesign it.

Independent monitoring requires a separate official CLI sign-in. SlopBar rejects a monitoring login whose refresh token equals a known CLI login and verifies that its account and organization match the selected slot. A successful monitoring login is stored separately under `monitoring`, protected by Windows DPAPI for the current Windows user. It is never used for account switching or exported to a CLI. Temporary CLI sign-in files are removed after completion/failure/timeout; an abrupt app or machine crash can leave a temporary `.slopbar-login-*` folder in the selected profile. WSL login folders are restricted to their owner before authentication runs.

Sign-in removes inherited `CLAUDE_*`, `ANTHROPIC_*`, `CODEX_*`, and `OPENAI_*` overrides. Windows disables cmd AutoRun and sets both Claude config and secure-storage directories to the temporary folder. WSL runs the CLI through `env -i` with an allowlist after loading the user's login profile. This prevents profile exports from redirecting the login's client, endpoints, or credential store. A failed import attempts the CLI's logout with that same isolated environment before removing the folder. If Claude uses Credential Manager rather than writing its credentials file, import currently fails and takes this cleanup path; native Credential Manager discovery/import is not implemented.

On Windows, the sign-in process is assigned to a kill-on-close job object; failure to attach aborts the sign-in. This limits console processes outliving SlopBar, but WSL process termination still needs a native integration test. At startup, SlopBar attempts isolated logout and removes abandoned folders older than 15 minutes. Cleanup requires the exact generated name and either its ownership marker or a regular legacy CLI credentials file, and excludes directory/credential symlinks. Unrecognized folders are left alone. Concurrent connect, disconnect and account removal share an account reservation through their final disk mutation.

Only independently owned monitoring sessions are refreshed. Imported CLI refresh tokens are never sent to a token endpoint. Refreshes are serialized; new refresh tokens are saved atomically before normal polling resumes, using Windows write-through replacement. If a write fails after rotation, the new token is retained in memory and persistence is retried without replaying the old token. Exiting before that write succeeds can require reconnecting. A transport failure that may have sent a request permits one replay after five minutes; its budget and backoff are persisted. Explicit rejection is terminal. A second uncertain result stops automatic replay and offers reconnecting. Replay may trigger provider reuse detection; its scope across independent sessions is not publicly guaranteed and needs live testing. Saved scopes and explicit refresh-token expiry are preserved; no refresh-token lifetime is invented when the server omits it. HTTP redirects are disabled for authentication and usage requests; token values and response bodies are not returned to the UI.

Disconnect removes local monitoring credentials even when the provider is unavailable, then attempts revocation of that monitoring token. Replacing a monitoring login saves the new login first and attempts revocation of the old chain. Server revocation is best effort; a failed disconnect revocation is reported in the UI. Account removal also attempts revocation. Imported CLI sessions are never revoked by these actions.

Authentication and usage requests go over HTTPS directly to the providers: `api.anthropic.com` and `platform.claude.com` for Claude, `chatgpt.com` and `auth.openai.com` for Codex. Monitoring does not send model prompts. The usage cache contains readings and timestamps, not authentication tokens. The non-Windows headless test build uses owner-only files rather than DPAPI; the desktop app targets Windows.

These OAuth sessions are credentials, not read-only usage API keys. DPAPI protects files at rest, but a compromised SlopBar process or code running as the same user can still misuse them. This change does not eliminate application, dependency, or update supply-chain risk.

Local builds have upstream updates disabled at compile time. Official release builds explicitly enable `upstream-updates`; those updates must match the signing key built into the app. Signatures authenticate a publisher, not the safety of a release.

## Reporting a vulnerability

Please report upstream security issues privately through [GitHub's private vulnerability reporting](https://github.com/thelioo/slopbar/security/advisories/new) instead of opening a public issue.
